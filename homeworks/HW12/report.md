# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Датасет `S12-hw-dataset.csv`, прогноз одномерного числового ряда `target` по времени.
- Разбиение `train / validation / test` выполнено по времени (примерно 70% / 15% / 15%) без перемешивания.
- Сравнены подходы: B1 (`naive-last`), B2 (`moving-average`), B3 (`ridge-lag-features`), R1 (`gru-forecast`).
- Лучшая модель выбирается по `validation MAE`, затем один раз измеряется качество на `test`.

## 2. Среда и воспроизводимость

- Python: 3.12.2
- pandas / numpy / scikit-learn: 2.2.2 / 1.26.4 / 1.6.1
- torch: 2.7.1+cu118
- Устройство (CPU/GPU): определяется автоматически в `HW12.ipynb` (в текущих прогонах использовалась `cuda`, если доступна, иначе `cpu`).
- Seed: 42 (фиксируется в ноутбуке для `random`, `numpy`, `torch`).
- Как запустить: открыть `HW12.ipynb` и выполнить Run All.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: `target`
- Частота временного ряда: почасовая, по датам из колонки `date`.
- Горизонт прогноза: один шаг вперёд.
- Размер датасета: 4320 наблюдений.
- Диапазон дат: с `2025-01-01 00:00:00` по `2025-06-29 23:00:00`.
- Есть ли дополнительные внешние признаки: в данной постановке использовался только одномерный ряд `target`.
- Комментарий: ряд демонстрирует выраженный сезонный суточный и недельный паттерн вокруг среднего уровня порядка 135 единиц, без пропусков. Наблюдаются умеренные колебания и отдельные выбросы, но без резких структурных разрывов, поэтому задача сводится к прогнозированию плавно меняющегося с сезонностью ряда.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: последовательное разбиение временного ряда на ранние, средние и поздние даты.
- Какие доли или интервалы использовались: около 70% на train, 15% на validation, 15% на test.
- Почему `random split` здесь некорректен: нарушает причинно-временной порядок и даёт утечку информации из будущего в прошлое.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: `lag_1`, `lag_7`, `lag_14`.
- Какие rolling-признаки использовались: `rolling_mean_7`, `rolling_std_7`.
- Какие календарные признаки использовались: день недели (`dow`).
- Как обрабатывались пропуски после построения лагов/rolling: строки с NaN, появившимися из-за сдвигов и окон, удалялись.
- Использовалось ли масштабирование и где именно оно обучалось: `StandardScaler` обучался только на train и применялся к validation и test.

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- B1 (`naive-last`): прогноз равен последнему известному значению ряда (наивный baseline).
- B2 (`moving-average`): прогноз равен скользящему среднему по окну (например, 7 последних значений).
- B3 (`ridge-lag-features`): линейная модель `Ridge` по лаговым, rolling- и календарным признакам.
- R1 (`gru-forecast`): модель `GRU` на оконном представлении ряда с фиксированным `window_size`.

Дополнительно:

- Основная метрика выбора лучшей модели: `MAE` на validation.
- Дополнительные метрики: `RMSE`, `MAPE`.
- `window_size` для `GRU`: 30 (см. конфиг в `best_gru_config.json`).
- Batch size: 64.
- Максимальное число эпох: 50.
- Optimizer: Adam.
- Learning rate: 1e-3.
- Как сохранялась лучшая модель: по наилучшему значению валидационного `MSE` (loss), в файл `artifacts/best_gru.pt`.

- Лучший baseline среди `B1`, `B2`, `B3`: `B1 (naive-last)` с `val_MAE ≈ 6.44`, `val_RMSE ≈ 8.20`, `val_MAPE ≈ 4.40%`.
- Полная статистика baseline-моделей на validation: `B2` (moving average) заметно хуже (`val_MAE ≈ 12.70`), `B3` (Ridge на признаках) лучше наивного по ряду метрик, но уступает `R1`.
- Лучшая `val_MAE` по всем подходам: `R1 (GRU)` — `val_MAE ≈ 4.91`, `val_RMSE ≈ 6.38`, `val_MAPE ≈ 3.33%` (после последнего прогона ноутбука).

- Для `GRU` в `DataLoader` используется `shuffle=False`, чтобы не перемешивать окна при обучении в постановке временного ряда.
- Лаговые и rolling-признаки в `B3` заметно улучшают наивный baseline, но рекуррентная модель на validation оказалась сильнее.

## 7. Анализ

Наивный baseline `B1` оказался достаточно сильным, так как почасовой ряд `target` меняется относительно плавно и ближайшее прошлое значение даёт уже неплохое приближение к будущему. Модель `B2` на скользящем среднем показала худшие метрики: сглаживание по окну из нескольких прошлых точек приводит к запаздыванию прогноза и потере резких локальных изменений. Лаговые и rolling-признаки в `B3 (Ridge)` добавили информации о более длинной истории и сезонности, благодаря чему качество оказалось конкурентоспособным на validation, но заметно лучше наивного подхода модель не стала.

Модель `GRU` на оконном представлении ряда (`R1`) лучше всего сработала на validation и была выбрана для единственной финальной проверки на test. По отложенному test метрики остаются в том же порядке величины, что и на validation, без сравнения с другими моделями на test (их test-метрики в `runs.csv` намеренно не заполняются). Тренд и сезонность (суточные/недельные циклы) хорошо видны на графиках и объясняют, почему модели, опирающиеся на историю (лаги, rolling, рекуррентная сеть), работают лучше слишком сильно сглаживающего прогноза.

Потенциальные утечки данных в такой задаче могли бы возникать при построении признаков с использованием будущих значений (rolling без сдвига назад), при обучении скейлеров по всему датасету или при использовании test-части для подбора гиперпараметров. В реализованной постановке эти риски учтены: split сделан по времени, признаки строятся только из прошлого, масштабирование и обучение моделей выполняются исключительно на train, а выбор лучшего подхода происходит по validation. Выбор по validation принципиален, потому что test должен оставаться честной финальной проверкой, а не частью процесса настройки модели. Наиболее показательные ошибки моделей наблюдаются на участках с быстрыми локальными изменениями ряда: на них сильнее всего страдает moving average, а GRU иногда переоценивает или недооценивает амплитуду колебаний.

## 8. Итоговый вывод

В качестве базового подхода для такой задачи я бы использовал комбинацию наивного baseline и линейной модели на лаговых/rolling-признаках: они просты в реализации, легко интерпретируются и уже дают качество, сравнимое с более сложными методами. Простых baseline (B1/B3) достаточно, когда нужно быстро получить ориентировочный прогноз на относительно стабильном ряде, без строгих требований к минимизации ошибки и без необходимости моделировать сложные нелинейные эффекты. Переход к `GRU` и другим нейросетевым моделям оправдан, когда важна работа с длинной историей, сложной сезонностью и нелинейностями, а также когда есть достаточно данных и ресурсов на настройку.

Главный вывод по части валидации временных рядов: критично сохранять причинно-временной порядок и оценивать модели на будущих интервалах, которые не использовались при обучении и настройке. `Random split` в такой задаче приводит к утечке информации из будущего и завышенным метрикам, поэтому корректный temporal split и аккуратная работа с признаками и масштабированием являются обязательным условием для достоверного сравнения моделей.
