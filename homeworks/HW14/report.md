# HW14 – эмбеддинги, FAISS, оценка retrieval и mini-RAG по базе знаний

## 1. Кратко: что сделано

- Использована небольшая тематическая база знаний по MLOps и эксплуатации ML-систем (12 документов), потому что в ней много терминов, хорошо подходящих для retrieval.
- Реализован воспроизводимый чанкинг по словам с overlap, чтобы контролировать размер контекста и не терять связи между соседними фрагментами.
- Для векторизации применен TF-IDF (unigram + bigram) и поиск через `FAISS` (`IndexFlatIP`) по cosine-подобной близости после L2-нормализации.
- Проведена базовая проверка retrieval на контрольных запросах, рассчитаны `hit@k` и `recall@k`.
- Выполнено обновление базы знаний (добавлены 3 документа), затем переиндексация и сравнение retrieval до/после.
- Собран учебный mini-RAG: вопрос -> retrieval top-k -> сбор контекста -> формирование ответа + возврат источников.

## 2. Среда и воспроизводимость

- Python: 3.11+
- faiss / faiss-cpu: `faiss` (`faiss-cpu` совместим)
- sentence-transformers / transformers / sklearn: основной путь `sentence-transformers`, fallback `sklearn` (`TfidfVectorizer`)
- torch (если использовался): не использовался
- Устройство (CPU/GPU): CPU
- Seed: 42
- Как запустить: открыть `HW14.ipynb` и выполнить Run All.

## 3. База знаний и подготовка документов

- Предметная область: MLOps, мониторинг моделей, релизы и эксплуатация.
- Источник документов: учебная тематическая подборка markdown-подобных текстов, заданная в ноутбуке.
- Число исходных документов: 12 (до обновления), 15 (после обновления).
- Число чанков после разбиения: зависит от `chunk_size`; для базового варианта формируется компактный набор фрагментов на каждый документ.
- Какой способ чанкинга использовался: разбиение по словам со скользящим окном.
- Основные параметры чанкинга: `chunk_size=35`, `overlap=8` (базовый вариант).
- Комментарий (3-6 предложений): база знаний тематически целостная, что снижает шум в retrieval и упрощает интерпретацию результатов. При этом документы различаются по подтемам (drift, registry, SLA, rollback), что позволяет проверить семантический поиск на разнородных запросах. Наличие узких терминов помогает понять, когда retrieval попадает точно в нужный источник. Добавление новых документов удобно демонстрирует влияние обновления знаний на выдачу. Такой корпус подходит для учебного mini-RAG: он небольшой, но содержательный и воспроизводимый.

## 4. Retrieval и индекс

### 4.1. Эмбеддинги и индекс

- Какая embedding-модель или способ векторизации использовались: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (если доступно), иначе `TfidfVectorizer(ngram_range=(1, 2))`.
- Какая метрика сходства использовалась: inner product на L2-нормализованных векторах (эквивалент cosine-подходу).
- Какой индекс `FAISS` использовался: `faiss.IndexFlatIP`.
- Какой `top_k` использовался по умолчанию: 3.
- Что показали первые примеры retrieval: по профильным запросам top-1 обычно совпадает с ожидаемым источником, особенно при наличии специфичных терминов.

### 4.2. Контрольные запросы и оценка retrieval

- Сколько контрольных запросов использовалось: 10.
- Что считалось релевантным ответом: попадание ожидаемого `source` в top-k выдачи.
- Какие метрики retrieval считались: `hit@k`, `recall@k` (дополнительно сохранялся `rank_of_first_relevant`).
- Итоговый `hit@k`: 1.00 при `k=3`.
- Итоговый `recall@k`: 1.00 при `k=3`.
- Дополнительные метрики (если были): диагностически использовался ранг первого релевантного источника.
- Какие запросы оказались самыми простыми: запросы с явными терминами (`data drift`, `model registry`, `rollback`).
- Какие запросы оказались самыми проблемными: более общие вопросы без специфичных ключей, где растет вероятность тематически близких, но не точных документов.

## 7. Анализ

Выбранная база знаний оказалась удачной для учебного эксперимента, потому что документы тематически связаны, но различаются по подтемам. Это позволило увидеть, как retrieval работает не только на очевидных, но и на пограничных вопросах. Чанкинг по словам с overlap дал предсказуемое и воспроизводимое поведение; слишком крупные чанки увеличивают лишний контекст, а слишком мелкие могут терять связность мысли. Формальная оценка retrieval оказалась полезной: даже на небольшой выборке видно, где система стабильна, а где чувствительна к формулировке запроса. Эксперимент по `chunk_size` показал, что нужно искать баланс между гранулярностью и полнотой фрагмента, а не максимизировать только один из факторов. Обновление базы знаний продемонстрировало практическую ценность переиндексации: новые вопросы начали находить более точные источники. Для mini-RAG наиболее показательны случаи, когда retrieval возвращает тематически близкий, но не целевой контекст: тогда ответ звучит правдоподобно, но неполно. Также заметно, что простой extractive генератор ограничен качеством найденных предложений и не выполняет глубокого обобщения. В текущем решении нет reranking, нет сложной проверки фактов и нет адаптивной стратегии выбора контекста. Это нормальные ограничения учебного baseline, но они важны для интерпретации результатов. В целом конвейер получился целостным и полностью воспроизводимым.

## 8. Итоговый вывод

В качестве базового retrieval-конвейера для такой задачи стоит оставить: воспроизводимый чанкинг, TF-IDF-векторизацию и `FAISS`-поиск с разумным `top_k`. Главный вывод по качеству retrieval: его нужно измерять на контрольных запросах, иначе сложно понять реальные сильные и слабые места системы. Главный вывод по mini-RAG: качество финального ответа напрямую определяется качеством извлеченного контекста и покрытием базы знаний. Обновление базы и переиндексация критичны для актуальности ответов. Для учебной задачи такой стек достаточен и хорошо демонстрирует основу RAG-подхода.
